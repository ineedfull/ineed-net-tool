# IP 探测并发优化 · 2026-09-21

## 原因与实现
- 原实现已有异步地址池，但默认仅 8 路，每个地址先等 ICMP 再逐个等 TCP 端口；扫描 Ping 子进程多等 700ms。
- 地址池默认 32 路，允许 1～128；同一 IP 的 ICMP/TCP/端口并行执行，第一个有效响应取消其余检查并等待释放资源。
- 全局原生探测池限制为 128 个活动进程/套接字，避免 128 地址 × 9 方法无界扩张。
- 保留用户响应超时，扫描的 Ping 进程退出余量缩至 50ms；独立 Ping 工具保留原行为。
- 扫描结果按 50ms 或 64 条批量刷新，结束前先交付全部剩余行，持久化完成后再发终态。
- 暂停使用共享唤醒 Promise，替代每路 80ms 的轮询；停止会清理运行中和排队中的探测。
- UI 显示并发地址数、耗时、完成数量与吞吐率。采用异步 I/O 并发，不引入 CPU worker_threads。

## 实际前后对比
同一台 macOS，32 个回环目标 `127.0.0.2-127.0.0.33`，无响应数均为 32、有效响应均为 0，用户配置超时均为 300ms。TCP 端口为 80/443。

| 方法 | 修改前 8 路 | 修改后 8 路 | 修改后默认 32 路 |
|---|---:|---:|---:|
| ICMP | 4033ms | 1433ms | 374ms |
| ICMP + TCP | 6434ms | 1426ms | 370ms |

这是一次本地无响应场景测量，说明等待与调度开销减少，不代表所有现场网络均能获得同样倍数。TCP 拒绝连接仍作为“有响应、端口未开放”展示。较高并发的最佳值受本机资源与网络限速影响。

当前版本可复测：`node scripts/benchmark-scan.mjs`（只探测固定回环范围）。修改前数据在修改原执行模块前用相同 NetworkTasks API 和参数测得。
